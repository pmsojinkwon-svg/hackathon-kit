# review — 다른 눈으로 검토

> **언제:** 제출 50분 전 (12:10), 또는 큰 기능 하나 끝났을 때.
> **부르는 법:** **새 터미널 탭을 열고 `codex`를 새로 켠 다음** `skills/review/SKILL.md 읽고 진행해줘`
> **왜 새로 켜나:** 만든 AI가 자기 코드를 검토하면 자기 실수를 못 본다. 기억 없는 새 AI가 "처음 보는 사람" 역할을 해야 함. 코파톤 상위권이 쓴 방식.
> **핵심:** 고치지 않는다. 질문 4개에만 답한다.

---

## 에이전트가 할 일

### 1단계. 목적 파악
`docs/PLAN.md`를 읽고 이 코드가 뭘 위해 만들어졌는지 파악한다.

### 2단계. 코드 읽기
큰 파일은 핵심 부분만.

### 3단계. 네 가지 질문에만 답하기 (각 3개 이하)

```
## 1. 돌아가나
- 서버 켜짐: (직접 켜봄 → OK / FAIL)
- PLAN 성공 기준 중 코드에서 구현이 안 보이는 것:

## 2. 어디서 깨지나 (문제 상황 시나리오)
- (상황) → (무슨 일이 생기나) → (심각도: 높음 / 중간 / 낮음)
  예: 데이터 파일이 비어있을 때 → 화면이 빈 채로 멈춤 → 중간

## 3. 문서와 코드가 맞나
- DECISIONS.md에 적힌 것 중 실제 코드와 다른 것:
- 코드에 있는데 DECISIONS.md에 없는 큰 선택:

## 4. 처음 보는 사람이 헷갈릴 곳
- (파일:줄) (왜)
```

### 4단계. 보고하고 멈춤

## 에이전트가 하지 않는 것
- 코드 수정
- 스타일·취향 지적
- "이렇게 했으면 더 좋았을 텐데" 식 재설계 제안 (시간 없음)
- PLAN 밖 기능 제안

## 나(사용자)가 할 일
- **2번(어디서 깨지나)**은 서술형 질문으로 거의 그대로 나옴. 읽고 기억해둔다
- **3번(문서와 코드 불일치)**은 반드시 고친다 — 심사 AI가 문서와 코드를 대조함
- 1번에서 FAIL 나온 것만 **원래 세션(만든 AI)**에게 가져가서 고치게 한다
